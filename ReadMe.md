
# 🕵️ Dark Web Threat Monitoring System<br><br>A Python-based **threat intelligence and dark web monitoring tool** designed to identify potential security threats, exposed organizational information, exploit discussions, and suspicious access-sale advertisements from authorized intelligence sources.<br><br>The system analyzes collected forum posts, extracts Indicators of Compromise (IOCs), calculates risk scores, and generates alerts when content matches configured threat categories or organizational watchlists.<br><br>Built as an educational cybersecurity and OSINT project, it supports both **offline sample analysis and Tor-based collection**.<br><br>> [!IMPORTANT]<br>> **Ethical Use & Data Protection**<br>><br>> This project is intended for defensive security research and authorized monitoring. It does not purchase, use, or intentionally redistribute leaked data. Passwords are redacted, and email addresses are masked before storage or reporting.<br>><br>> Use only lawful, authorized sources. Do not access stolen accounts, interact with criminal marketplaces, download suspicious files, or follow untrusted links. The sample mode uses fictional data for safe demonstrations.<br><br>---<br><br>## 📌 Table of Contents<br><br>- [Overview](#-overview)<br>- [Key Features](#-key-features)<br>- [System Architecture](#-system-architecture)<br>- [How It Works](#-how-it-works)<br>- [Technologies Used](#-technologies-used)<br>- [Project Structure](#-project-structure)<br>- [Requirements](#-requirements)<br>- [Installation](#-installation)<br>- [Usage](#-usage)<br>- [Risk Scoring](#-risk-scoring)<br>- [Indicators of Compromise](#-indicators-of-compromise)<br>- [Watchlist Configuration](#-watchlist-configuration)<br>- [Output and Reports](#-output-and-reports)<br>- [Privacy and Security](#-privacy-and-security)<br>- [Limitations](#-limitations)<br>- [Future Improvements](#-future-improvements)<br>- [Disclaimer](#-disclaimer)<br><br>---<br><br>## 🔍 Overview<br><br>Organizations can face threats when credentials, network access, vulnerabilities, or internal information appear in underground discussions and other publicly accessible intelligence sources.<br><br>Manually tracking such information can be time-consuming. This project provides a modular pipeline to collect permitted content, analyze it automatically, and highlight potentially relevant threats.<br><br>### What does it do?<br><br>- Collects posts from configured sources or local HTML files.<br>- Extracts relevant information from forum pages.<br>- Identifies potential IOCs, including IP addresses, CVE identifiers, hashes, and credential-like patterns.<br>- Categorizes posts based on threat-related keywords.<br>- Matches content against an organization's domains and keywords.<br>- Calculates a risk score for each analyzed post.<br>- Stores deduplicated findings in a SQLite database.<br>- Generates console alerts and machine-readable JSON reports.<br><br>**Primary objective:** Help defenders prioritize potentially relevant threat intelligence without manually reviewing every collected post.<br><br>---<br><br>## ✨ Key Features<br><br>| Feature                   | Description                                                                               |<br>| ------------------------- | ----------------------------------------------------------------------------------------- |<br>| 🧅 Tor Integration        | Retrieve configured pages through a Tor SOCKS proxy                                       |<br>| 🧪 Offline Sample Mode    | Demonstrate the pipeline using fictional data without Tor                                 |<br>| 🔎 IOC Extraction         | Identify potential IPs, hashes, CVEs, and credential patterns                             |<br>| 🏷️ Threat Classification | Categorize credentials, exploits, malware, ransomware, and access sales                   |<br>| 🎯 Organization Watchlist | Detect mentions of monitored domains and keywords                                         |<br>| 📊 Risk Scoring           | Assign risk levels to findings based on configured scoring rules                          |<br>| 🗄️ SQLite Storage        | Maintain a local history of analyzed findings                                             |<br>| ♻️ Deduplication          | Reduce repeated records from recurring observations                                       |<br>| 🚨 Threat Alerts          | Display findings ranked by risk                                                           |<br>| 📄 JSON Reports           | Export findings to `reports/latest.json`                                                  |<br>| 🔐 Data Redaction         | Mask email addresses and replace passwords with `[REDACTED]` before storage and reporting |<br><br>*These are intended capabilities; their actual coverage depends on the implementation, source data, and configured parsing rules.*<br><br>---<br><br>## 🏗️ System Architecture<br><br>The project uses a modular architecture in which each component handles a specific stage of the threat-intelligence workflow.<br><br>```mermaid<br>flowchart TD<br>    A[Authorized Sources] --> B[fetcher.py]<br>    S[Local Sample Data] --> B<br>    B --> C[parser.py]<br>    C --> D[analyzer.py]<br>    D --> E[IOC Extraction]<br>    D --> F[Threat Classification]<br>    D --> G[Watchlist Matching]<br>    E --> H[Risk Scoring]<br>    F --> H<br>    G --> H<br>    H --> I[storage.py]<br>    I --> J[(SQLite Database)]<br>    I --> K[Console Alerts]<br>    I --> L[reports/latest.json]<br>```<br><br>### Data flow<br><br>1. **Collection:** Fetch permitted source pages through Tor or load local sample content.<br>2. **Parsing:** Extract relevant text and metadata from HTML.<br>3. **Analysis:** Identify potential indicators, classify threats, and match watchlist entries.<br>4. **Scoring:** Calculate a risk score based on the configured categories and matches.<br>5. **Storage:** Deduplicate and save findings to SQLite.<br>6. **Reporting:** Display alerts and produce a JSON report for further analysis.<br><br>---<br><br>## ⚙️ How It Works<br><br>### 1. Data collection<br><br>`fetcher.py` handles source retrieval, Tor connectivity checks, and offline loading.<br><br>### 2. HTML parsing<br><br>`parser.py` uses BeautifulSoup to extract information such as:<br><br>- Post title<br>- Author or username, when available<br>- Publication date, when available<br>- Main post body<br><br>The HTML selectors may need to be adapted for different page layouts.<br><br>### 3. Threat analysis<br><br>`analyzer.py` processes the extracted text to identify:<br><br>- Credential-like patterns<br>- CVE identifiers<br>- IP addresses<br>- File hashes<br>- Exploit and malware discussions<br>- Ransomware-related content<br>- Network access advertisements<br>- Mentions of monitored organizations<br><br>It also applies keyword-based category scoring and watchlist matching. TF-IDF keyword extraction can help identify terms that are distinctive within a collection of posts.<br><br>### 4. Risk assessment<br><br>Each finding receives a numeric score based on configured threat categories, organizational relevance, and other scoring conditions.<br><br>### 5. Storage and alerts<br><br>`storage.py` maintains the local SQLite database and handles deduplication. The monitoring interface displays prioritized findings and produces a JSON report.<br><br>---<br><br>## 🧰 Technologies Used<br><br>- **Python** — Core application and analysis pipeline<br>- **Requests / SOCKS support** — HTTP retrieval through a configured proxy, depending on `requirements.txt`<br>- **Tor** — Network routing for supported onion-service access<br>- **BeautifulSoup** — HTML parsing<br>- **Regular Expressions** — Pattern-based IOC extraction<br>- **TF-IDF** — Keyword relevance analysis<br>- **SQLite** — Local threat-intelligence storage<br>- **JSON** — Configuration and report formats<br>- **argparse** — Command-line options<br><br>---<br><br>## 📁 Project Structure<br><br>```text<br>dark-web-threat-monitor/<br>│<br>├── fetcher.py              # Tor retrieval and offline loader<br>├── parser.py               # Forum HTML parsing<br>├── analyzer.py             # IOC extraction and threat scoring<br>├── storage.py              # SQLite persistence and deduplication<br>├── monitor.py              # Command-line entry point<br>│<br>├── watchlist.json          # Organization domains and keywords<br>├── requirements.txt        # Python dependencies<br>│<br>├── threats.db              # Generated SQLite database<br>│<br>└── reports/<br>    └── latest.json         # Generated threat report<br>```<br><br>*Generated files may appear only after the first successful run. Adjust this layout to match the actual repository.*<br><br>---<br><br>## 💻 Requirements<br><br>Before running the project, ensure you have:<br><br>- Python 3 installed<br>- `pip` available<br>- The dependencies listed in `requirements.txt`<br>- Tor Browser or a configured Tor service for live collection<br>- Internet access for installing dependencies and retrieving permitted sources<br>- Permission to access and analyze the configured sources<br><br>**For the first run, Tor is not required.** The offline sample mode is the recommended starting point.<br><br>---<br><br>## 🚀 Installation<br><br>### 1. Clone the repository<br><br>Replace the placeholders with your actual GitHub username and repository name.<br><br>```bash<br>git clone https://github.com/YOUR_USERNAME/YOUR_REPOSITORY.git<br>```<br><br>### 2. Open the project directory<br><br>```bash<br>cd YOUR_REPOSITORY<br>```<br><br>### 3. Install dependencies<br><br>```bash<br>python -m pip install -r requirements.txt<br>```<br><br>If your system uses the `py` launcher, you can use:<br><br>```bash<br>py -m pip install -r requirements.txt<br>```<br><br>---<br><br>## ▶️ Usage<br><br>### 🧪 Option 1: Run the sample demonstration<br><br>Start with fictional sample data to test the pipeline without connecting to Tor.<br><br>```bash<br>python monitor.py --sample<br>```<br><br>To display only findings at or above the HIGH threshold:<br><br>```bash<br>python monitor.py --sample --min-level HIGH<br>```<br><br>This is the recommended way to verify parsing, analysis, scoring, storage, and reporting before enabling live collection.<br><br>### 🧅 Option 2: Run through Tor<br><br>1. Install Tor Browser from the official Tor Project website.<br>2. Start Tor Browser and confirm that its SOCKS proxy is available.<br>3. Use a permitted source URL and the appropriate proxy configuration.<br><br>Example command:<br><br>```bash<br>python monitor.py --url http://EXAMPLE.onion/forum --proxy socks5h://127.0.0.1:9150<br>```<br><br>Replace the placeholder with a source you are authorized to monitor.<br><br>Common proxy configurations:<br><br>| Tor configuration      | Typical SOCKS address |<br>| ---------------------- | --------------------- |<br>| Tor Browser            | `127.0.0.1:9150`      |<br>| Standalone Tor service | `127.0.0.1:9050`      |<br><br>The actual port depends on your Tor configuration. The `socks5h` scheme requests hostname resolution through the proxy, which is useful for onion-service addresses.<br><br>### 📄 Option 3: Analyze multiple URLs<br><br>Place one permitted URL per line in a text file named `urls.txt`:<br><br>```text<br>http://EXAMPLE1.onion/forum<br>http://EXAMPLE2.onion/posts<br>```<br><br>Then run:<br><br>```bash<br>python monitor.py --urls-file urls.txt<br>```<br><br>If your implementation requires a proxy for live retrieval, provide the configured proxy option as well:<br><br>```bash<br>python monitor.py --urls-file urls.txt --proxy socks5h://127.0.0.1:9150<br>```<br><br>**Note:** These commands assume the listed command-line arguments are implemented by `monitor.py`. Check `python monitor.py --help` if an option is unavailable.<br><br>---<br><br>## 📊 Risk Scoring<br><br>The analyzer assigns points to findings based on the threat categories and watchlist matches it detects.<br><br>### Configured scoring model<br><br>| Detection                    | Points |<br>| ---------------------------- | -----: |<br>| Credential-related content   |    +30 |<br>| Exploit-related content      |    +35 |<br>| Network access for sale      |    +40 |<br>| Ransomware-related content   |    +40 |<br>| Malware-related content      |    +25 |<br>| Organization watchlist match |    +40 |<br>| Large credential dump        |    +10 |<br><br>The final score is capped at 100.<br><br>### Risk levels<br><br>| Level       |    Score |<br>| ----------- | -------: |<br>| 🟢 LOW      | Below 30 |<br>| 🟡 MEDIUM   |    30–54 |<br>| 🟠 HIGH     |    55–79 |<br>| 🔴 CRITICAL |   80–100 |<br><br>### Example<br><br>Suppose a post mentions an exploit and a monitored organization:<br><br>- Exploit-related content: +35<br>- Watchlist match: +40<br>- Total: 75<br><br>The resulting risk level is **HIGH**.<br><br>If the same post triggers several categories, their points may accumulate. The score is therefore a prioritization heuristic, not a calibrated probability that an attack will occur.<br><br>**Important:** A keyword match does not establish that a leak is authentic, that a credential is valid, or that an organization has been compromised. Findings require validation through authorized channels.<br><br>---<br><br>## 🔎 Indicators of Compromise (IOCs)<br><br>The analyzer is designed to extract several classes of indicators from post text.<br><br>| Indicator          | Example                           | Purpose                                                     |<br>| ------------------ | --------------------------------- | ----------------------------------------------------------- |<br>| CVE identifier     | `CVE-2025-12345`                  | Identify a vulnerability reference                          |<br>| IPv4 address       | `192.0.2.10`                      | Identify a potential network indicator                      |<br>| File hash          | A 64-character hexadecimal string | Identify a potential SHA-256 hash                           |<br>| Email pattern      | `u***@example.com`                | Identify a masked email reference                           |<br>| Credential pattern | `email:[REDACTED]`                | Flag credential-like content without retaining the password |<br><br>Examples are illustrative and may not correspond to real vulnerabilities, accounts, or threats.<br><br>IOC extraction is pattern-based and may produce false positives. IP addresses, hashes, and vulnerability references should be validated before being used in security decisions.<br><br>---<br><br>## 🎯 Watchlist Configuration<br><br>The organization watchlist is maintained in `watchlist.json`.<br><br>Example configuration:<br><br>```json<br>{<br>  "domains": [<br>    "example.com",<br>    "example.org"<br>  ],<br>  "keywords": [<br>    "Example Organization",<br>    "Example Product",<br>    "Example Internal Portal"<br>  ]<br>}<br>```<br><br>Replace these examples with approved monitoring terms for your organization.<br><br>### Recommended practices<br><br>- Monitor only domains and keywords you are authorized to investigate.<br>- Prefer distinctive company and product names to reduce false positives.<br>- Avoid adding personal information unless there is a clear, lawful need.<br>- Review matches manually before escalating an alert.<br>- Keep watchlists out of public repositories if they reveal sensitive internal information.<br><br>The exact JSON keys must match the schema expected by your implementation.<br><br>---<br><br>## 📂 Output and Reports<br><br>The system is designed to produce three main outputs.<br><br>### 1. Console alerts<br><br>Findings are displayed with their risk levels and relevant indicators. The minimum-level option can help reduce noise.<br><br>### 2. SQLite database<br><br>```text<br>threats.db<br>```<br><br>The database provides a local history of analyzed findings and supports deduplication.<br><br>### 3. JSON report<br><br>```text<br>reports/latest.json<br>```<br><br>A report may contain fields such as:<br><br>- Post title and metadata<br>- Detected categories<br>- Risk score and risk level<br>- Relevant IOC references<br>- Watchlist match information<br>- Collection or analysis timestamp<br><br>The actual report fields depend on the implementation.<br><br>### Example report structure<br><br>The following is illustrative JSON, not a guaranteed representation of the generated file:<br><br>```json<br>{<br>  "title": "Example vulnerability discussion",<br>  "categories": [<br>    "exploit"<br>  ],<br>  "risk_score": 75,<br>  "risk_level": "HIGH",<br>  "watchlist_match": true,<br>  "indicators": [<br>    "CVE-2025-12345"<br>  ]<br>}<br>```<br><br>Sensitive content should be redacted before data reaches persistent storage or exported reports, not merely hidden in the console output.<br><br>---<br><br>## 🔐 Privacy and Security<br><br>The system is designed around data minimization and defensive analysis.<br><br>- **Password redaction:** Replace detected passwords with `[REDACTED]` before storage and reporting.<br>- **Email masking:** Mask email addresses when displaying or persisting findings, according to the configured policy.<br>- **Local storage:** SQLite and generated reports may contain sensitive intelligence and should be protected.<br>- **No active exploitation:** The intended workflow analyzes collected text rather than attempting to exploit vulnerabilities.<br>- **No marketplace transactions:** The project does not require buying access, purchasing data, or contacting criminal sellers.<br>- **Untrusted HTML:** Treat collected pages as hostile input. Do not execute scripts, download attachments, or follow embedded links.<br>- **Tor limitations:** Tor provides network-routing privacy, but it does not guarantee anonymity or make unauthorized activity lawful.<br><br>Avoid committing databases, reports, credentials, or sensitive watchlists to a public GitHub repository.<br><br>A `.gitignore` file can help prevent accidental publication:<br><br>```gitignore<br>__pycache__/<br>*.py[cod]<br>.venv/<br>venv/<br><br>threats.db<br>*.sqlite<br>*.sqlite3<br><br>reports/*<br>!reports/.gitkeep<br><br>urls.txt<br>.env<br>```<br><br>If your reports are intentionally sanitized and meant to be public, configure version control accordingly rather than publishing them automatically.<br><br>---<br><br>## ⚠️ Limitations<br><br>This project is an educational prototype and has several limitations.<br><br>- **Source coverage:** It only analyzes sources that can be lawfully accessed and successfully parsed.<br>- **HTML variability:** Forum layouts change, so CSS selectors may need updating.<br>- **Heuristic scoring:** Scores are based on configured rules, not a trained or calibrated threat-probability model.<br>- **False positives:** Common keywords and IOC patterns can produce irrelevant matches.<br>- **Incomplete intelligence:** A lack of findings does not prove that an organization has no exposure.<br>- **Credential detection:** Pattern matching cannot reliably determine whether credentials are genuine or active.<br>- **Privacy assurance:** Redaction must be applied consistently to database fields, logs, exceptions, and reports.<br>- **Tor reliability:** Proxy availability, connection failures, and onion-service downtime can interrupt collection.<br>- **Deduplication:** Repeated content may require normalization to identify equivalent posts reliably.<br>- **Legal restrictions:** The legality of accessing, processing, and retaining particular sources or information varies by jurisdiction.<br><br>---<br><br>## 🔮 Future Improvements<br><br>Potential enhancements include:<br><br>- [ ] Multi-page collection and pagination support<br>- [ ] Improved source-specific parsers<br>-
